## Purpose and shared assumptions

This reference preserves the completed advanced root-field runtime test for reconstruction and counting. **Test 4 is user-verified for the tested compact milestone serializer shape in both Element formula evaluation and actual Preview Export.** The fictional compact-JSON Deposit reconstruction/count fixture also passes `scripts/test_frontier_designs.py`; that local fixture is not an Element runtime emulator.

Every identifier is fictional. Replace markers only after inspecting a redacted evaluated root sample. Do not reuse the fictional values or an institution's prior identifiers.

## Test 4: count qualifying Deposit milestones

**Goal:** Count up to five `DEPOSIT` milestones that:

- have application GUID `school.applications.48217`;
- have either term `school.terms.59321` or `school.terms.59322`;
- do not have exact major `school.major.73104`, while a missing major is allowed; and
- have a date timestamp.

**Knowledge gaps exercised:** canonical type enumeration, raw occurrence guard, reconstructing an object whose metadata can precede `type`, exact independent property checks, and numeric `SUM`.

**Serializer assumptions:** each milestone object begins with `"name":`, the next object boundary is `},{"name":"`, and evaluated JSON is compact. Rebuild both prefix and suffix patterns when the sample differs.

**Status:** **User-verified** for the tested compact serializer shape. The complete five-slot formula produced the expected eight-case count matrix in Element formula evaluation and the user reported the same results in actual Preview Export. Portability to serializer shapes with different object-start ordering or completely omitted optional properties remains separately unverified.

### Runtime status of reconstruction mechanics

The following Test 4 mechanics were user-verified in September 2026 against a compact `[user-milestones-root]` value. Early probes were run in Element formula evaluation; the final assembled five-slot formula was later reported with matching results in formula evaluation and actual Preview Export.

- `SPLIT_INDEX([user-milestones-root], """type"":""DEPOSIT""", 2)` returned the content after the first Deposit marker, beginning with that Deposit's post-`type` fields and continuing through later milestone objects. This proves the first split alone does **not** isolate the target object.
- When only one Deposit existed, the same split at index `3` returned an empty string. On a zero-Deposit record, index `2` also returned an empty string. An outer `IF(... = "", ...)` guard therefore correctly reported the occurrence as absent in both cases.
- Prefix recovery with `REGEXP_EXTRACT(SPLIT_INDEX(..., marker, 1), ".*(""name"":.*)$")` returned only the current Deposit's fields from `name` through the field immediately before `type` in the tested compact serialization.
- Suffix bounding with `SPLIT_INDEX(SPLIT_INDEX(..., marker, 2), "},{""name"":"", 1)` returned only the current Deposit's fields after `type` and stopped before the following milestone object.
- Concatenating the recovered prefix, the canonical `"type":"DEPOSIT"` marker, and the bounded suffix reconstructed one complete Deposit object without text from the following milestone.
- Independent exact-marker checks against that reconstructed object were also user-verified: the supplied application GUID matched, the supplied term GUID matched, an exact major marker was detected and could be treated as excluded, and a deliberately nonmatching major marker was absent and therefore remained allowed.
- Nested `SPLIT_INDEX` timestamp extraction from the reconstructed object returned the exact 13-digit epoch-millisecond string from that Deposit's `date.$date.$numberLong` field. This verifies that the post-reconstruction property checks and timestamp extraction can stay scoped to the same bounded milestone object for the tested serializer shape.
- A combined candidate that joined exact application match, exact term match, exact-major exclusion, and timestamp-presence checks with `&` returned numeric `1` when every condition passed. Changing only the excluded-major test to the object's actual major returned `0`; changing only the term to a nonmatching value returned `0`; changing only the application to a nonmatching value returned `0`. This user-verifies conjunction behavior and numeric candidate output for the tested formula-evaluation context.
- A reconstructed Deposit whose serialized major property was `"major":null` was separately detected as a null-major object. Searching that same object for an exact quoted excluded-major marker returned blank, so the exact-exclusion architecture treated the null major as allowed. This user-verifies the intended "exclude only one exact major; allow null/missing-style values" behavior for an explicit `null` property in the tested serializer shape. An entirely omitted `major` property remains a logically related but separately unverified shape.
- Numeric aggregation through the raw occurrence guards was also user-verified. The same five-slot `SUM(IF(SPLIT_INDEX(...)="",0,1), ...)` architecture returned `1` for a record with one Deposit, `0` for a record with zero Deposits, and `2` for a record with two Deposits. This verifies that the guarded occurrence candidates aggregate as numeric values and that multiple real target occurrences contribute independently to `SUM` in the tested formula-evaluation context.
- Full per-occurrence business eligibility across two reconstructed Deposit objects was then user-verified. With the same application, term, exact-major exclusion, and timestamp-presence checks applied independently to occurrence 1 and occurrence 2, the four validity arrangements produced: invalid/valid -> `1`, valid/invalid -> `1`, valid/valid -> `2`, and invalid/invalid -> `0`. This verifies that later Deposit occurrences do not borrow eligibility metadata from earlier Deposits (or vice versa), and that `SUM` counts only the independently qualifying reconstructed objects in the tested formula-evaluation context.
- The two-Deposit business-eligibility probes above used manually created Deposit milestones and still passed under enumeration by the canonical `"type":"DEPOSIT"` marker. This user-verifies the full reconstruction/filter/count architecture on that manual-creation path rather than only on automatically created Deposit records. In the follow-up name diagnostic, the evaluated manual Deposit still serialized with `name` equal to `Deposit Page`, so that diagnostic does **not** independently prove an alternate display name. Keep alternate-name evidence separate: a previously user-verified record showed a qualifying manually/import-created Deposit named `Client Import` while its canonical type remained `DEPOSIT`.
- The five-slot occurrence ceiling was also user-verified directly. The raw occurrence-count probe returned `5` when the record contained exactly five Deposit occurrences and remained `5` when the record contained exactly six Deposit occurrences. This confirms that the five explicit slots cover occurrences 1-5 and that a sixth target occurrence is intentionally outside coverage rather than being accidentally counted.
- Explicit null-term rejection was user-verified on a reconstructed Deposit. The marker `"term":null` was detectable, while an exact allowed quoted-term marker was absent, so the term allow-list correctly rejected that Deposit. This verifies explicit-null handling for a required term; it does not by itself prove behavior for a completely omitted `term` property.
- The **complete five-slot Test 4 formula** was then exercised as one assembled expression using two exact allowed terms, one excluded major, required application GUID, required date, and the first-five-occurrence ceiling. The eight controlled cases returned `0`, `1`, `0`, `0`, `1`, `2`, `5`, and `5` for: zero Deposits; one qualifying Deposit; one excluded-major Deposit; one `term:null` Deposit; valid+invalid; two valid; five valid; and six valid. The user reported the same results for formula evaluation and actual Preview Export. This upgrades the assembled Test 4 formula from a design target to **user-verified Export behavior for the tested compact serializer shape**.

These observations verify the **reconstruction, independent property checks, combined single-candidate eligibility mechanics, explicit-null-major inclusion, explicit-null-term rejection, guarded numeric aggregation, two-occurrence business-eligibility counting, manual-creation-path compatibility, five-occurrence coverage ceiling, and the complete assembled five-slot count formula in both evaluation and Preview Export** for the observed compact serializer shape. They do not prove that every tenant/context always serializes milestone objects with `name` first, and they do not yet verify completely omitted `major` or `term` properties. Treat those serializer variations as separate portability tests rather than downgrading the verified Test 4 behavior for the tested shape.
